## What Yahmi is

A check a UAE small business runs **before paying a supplier invoice**:

- The business forwards the invoice (PDF or photo) and, optionally, the email it came with, on WhatsApp or the web.
- Yahmi answers **Stop / Check / OK**.
- Every warning names its source.
- Warnings say "verify with the supplier", never "this is fraud".

**Core insight:** every invoice or payment-diversion fraud must send money to an account the business has never paid, or one different from the supplier's usual account. The payment-history check flags that by construction, however convincing the email is. Everything else is supporting evidence.

### Invoice reader (`yahmi/extract.py`)

- **Text source:**
  - PDF: text layer via pdfplumber `layout=True`, with column-gap normalisation.
  - Photo: Tesseract OCR, rebuilt into lines and columns from word boxes.
  - If an OCR read doesn't reconcile, it retries with Arabic+English OCR and keeps the better read.
  - Eastern Arabic and Persian digits are normalised to Latin.
- **IBAN:** accepted only if the checksum passes, so an unconfirmed IBAN goes to the user to type.
- **Amounts:** found by VAT arithmetic (subtotal + VAT = total), not by label. `amounts_confident` is true only when that reconciles.
- **Supplier name:** label → header names above the customer block → "Account name" agreement → word-level merge of two OCR reads.
- **Invoice number:** label vocabulary plus value shape, same line or next line, with OCR repairs.

- We checked 46 real fraud emails by hand. All 34 invoice and wire frauds needed a new or changed account.
- This is a rule check, not a model test.
- Holdout v2 cannot extend this: it contains no payment-account frauds (credential and brand phishing only), and the training corpora are memorized, so the AI-miss complement has to be measured on real invoice/wire frauds in a future set (v4). v3 also had none.

## Strengths

- A clear core idea that catches every payment-diversion fraud by construction (new or changed account), whatever the email says.
- Explainable output: every warning cites its source; verify, don't accuse.
- Works on WhatsApp, so there is no app to install. Arabic replies.
- Privacy by design: keyed fingerprints, invoices deleted after reading, PDPL-aware.
- Honest evaluation culture: frozen models, untouched tests, published limits.
- Fits the UAE system: complements CBUAE Al Tareq Confirmation of Payee by acting earlier, when the invoice arrives.

## Weaknesses (be upfront about these)

- **No real UAE customer invoices tested yet.** Pilot data is pending.
- **Invoice reader is weak on real-world layouts** (see table above). This is the top engineering priority.
- **Email AI:** invoice-style frauds reach only amber; Arabic is weak; training data is small (~600 real emails) and skewed to published examples.
- **Government data not live:** the FTA TRN check sits behind a captcha. NER/DET/CBUAE need official API access, which is a pilot ask.
- **First-payment amber** may fire often for new businesses; the rate is not yet measured on real data.
- **Network warnings** need many users before they matter (cold start).
- **No production hardening:** single server, SQLite, no authentication or rate limiting.

## Evaluation rules

- **Holdout splits and frozen tests are never used for tuning.** This covers `split: holdout` in `eval/ext_*`, `data/real_invoices_uae`, `data/bec_frozen_test.json` and any future `*_holdout*` file. Run them once at the end, report the result, and record in `TODO.md` that the run happened.
- Thresholds (amber 0.62, red 0.80) are fixed in advance. Don't re-pick them on test data.
- Score with `eval/eval_extract.py <SET> pdf|jpg`. It skips null labels.
- Group cross-validation by source, never by random email, so near-duplicates don't leak.
